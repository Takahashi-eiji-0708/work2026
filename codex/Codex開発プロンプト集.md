# Codex 段階開発プロンプト集 — ELI Sales Assist を「動かしながら直して」作る

## この資料の使い方

この資料は、研修の第10章（開発トラック）で、OpenAI Codex に日本語で指示しながら
**ELI Sales Assist**（商談後の議事録・メール下書き・行動管理を支援するアプリ）を作るためのプロンプト集です。

**一度に完成品を作らせるのではなく**、次のサイクルを8つのステージで繰り返します。

```
① 作らせる（プロンプト） → ② 動かす（動作確認） → ③ 見つける（不具合）
      ↑                                                  ↓
⑥ テストで守る ← ⑤ 直させる（修正プロンプト） ← ④ 伝える（症状・再現手順）
```

| ステージ | 内容 | 目安 | 主な不具合のストーリー |
|---|---|---|---|
| 0 | 準備（AGENTS.md・雛形） | 10分 | `streamlit` が見つからない／モジュールが読み込めない |
| 1 | 商談メモの登録と一覧 | 15分 | 登録しても一覧に出ない／再起動すると消える |
| 2 | 議事録生成（モック → 実際の LLM に近づける） | 20分 | LLM の出力が ```json で囲まれていて読めない |
| 3 | 送信前マスキング | 15分 | 全角の電話番号がすり抜ける／直したら表示が変わった（副作用） |
| 4 | 名前の復元とメール下書き | 15分 | 議事録やメールに `[PERSON_1]` が残る／顧客向けメールに予算の話が入る |
| 5 | 行動管理 | 20分 | 期限が「今週金曜」のまま並ぶ／基準日がずれる／再生成で重複 |
| 6 | CSV 出力（Excel 連携） | 10分 | Excel で開くと文字化けする |
| 7 | 仕上げ（エラー処理・セキュリティ点検） | 20分 | API キー未設定で画面にエラーの詳細が出る |

**研修内の目標はステージ0〜4**（ステージ2まで動けば成功）。ステージ5〜7は持ち帰り課題です。

> **大切な前提**
> - Codex の出力は毎回変わります。**ここに書いた不具合が出ないこともあれば、別の不具合が出ることもあります**。
>   不具合が出なかった場合は、「動作確認」の手順で **問題がないことを確かめて** から次に進みます。
>   別の不具合が出た場合は、下の「不具合の伝え方」で伝えます。**それもこの研修の練習です**
> - 完成形（参照実装）は `app/` にあります。遅れた場合は、講師の指示で該当するファイルをコピーして追いつきます
> - **実際の顧客情報は入力しない**。`materials/` と `codex/testdata/` の架空データを使います

## 事前準備

### Codex について

- Codex は OpenAI のコーディングエージェントです。ターミナルで使う **Codex CLI**、VS Code などの **IDE 拡張**、クラウド上で動く形態があります。本研修では CLI または IDE 拡張を使います
- ChatGPT の対応プランでサインインするか、API キーで利用します（利用条件・料金は事前に確認）
- Codex は作業フォルダの **`AGENTS.md`** を読み、そこに書かれたルールに従います
- 承認モード（CLI では `/approvals`）は、**「作業フォルダ内の編集とコマンド実行は自動、それ以外は確認」** にします。フォルダ外への書き込みやネットワークアクセスを求められたら、内容を読んでから許可します

> Codex の画面・コマンド・モード名は更新されることがあります。講師が当日の画面で確認します。

## 不具合の伝え方（共通テンプレート）

「動きません」だけでは、Codex は推測で直そうとして、別の場所を壊すことがあります。次の型で伝えます。

```
次の不具合を直してください。

【症状】何が起きたか
【再現手順】1. … 2. … 3. …
【期待する動作】本来どうなってほしいか
【エラーメッセージ】（あれば貼る。顧客情報が含まれていないか確認してから）

進め方：
- まず原因を説明してから修正してください
- この不具合を再現するテストを先に追加し、修正後にテストが通ることを確認してください
- AGENTS.md のルールを守り、このステージに関係ないファイルは変更しないでください
```

## ステージ1 商談メモの登録と一覧（15分）

**ゴール**：商談を登録でき、アプリを再起動しても残っている

### プロンプト

```
ステージ1：「商談登録」タブを作ってください。

- 入力項目：顧客名（必須）、商談日（必須・日付）、出席者、商談メモ（必須・複数行）
- 「登録する」ボタンで保存し、同じタブの下に登録済みの商談を新しい順に一覧表示する
- 一覧では、商談日・顧客名と、メモの先頭100文字を表示する
- 必須項目が空のときはエラーメッセージを表示して保存しない
- 保存処理は sales_assist/ の中にまとめてください
- テストも追加してください
```

### 動作確認

1. `testdata/04_短い商談メモ.txt` の内容を貼り付けて登録する → **すぐに** 一覧に表示されるか
2. もう1件登録する → 新しい順に並ぶか、入力欄が空に戻るか
3. 顧客名を空にして登録 → エラーが出て保存されないか
4. **アプリを止めて（Ctrl＋C）もう一度起動** → 登録した商談が残っているか

### 想定される不具合

**不具合1-A：登録しても一覧にすぐ表示されない（もう一度何か操作すると表示される）**

- 原因：Streamlit は画面を上から順に描画するため、一覧を描いた **後で** 保存している
- 修正プロンプト

```
【症状】商談を登録しても、直後は一覧に表示されません。別のボタンを押すなど、もう一度操作すると表示されます。
【再現手順】1. 商談を入力 2. 「登録する」を押す 3. 一覧を見る
【期待する動作】「登録する」を押した直後に一覧に表示される。入力欄は空に戻る。
（以下、共通テンプレートの「進め方」）
```

**不具合1-B：アプリを再起動すると、登録した商談が消える**

- 原因：`st.session_state`（画面を開いている間だけのメモリ）に保存している
- 修正プロンプト

```
【症状】アプリを再起動すると、登録した商談がすべて消えます。
【期待する動作】再起動しても残るように、SQLite（DB_PATH で指定したファイル）に保存してください。
テーブル設計を説明してから実装し、「別の接続から読み直しても残っている」ことを確かめるテストを追加してください。
```

### 完了チェック

- [ ] 登録直後に一覧に表示される
- [ ] 再起動しても残る
- [ ] `data/` フォルダが `.gitignore` に入っている（商談データをコミットしない）

## ステージ2 議事録生成（20分）

**ゴール**：登録した商談から、決まった型の議事録を生成して表示する

### ステップ2-A：モックで作る

```
ステージ2-A：「議事録」タブを作ってください。

- 登録済みの商談を選び、「議事録を生成」ボタンで議事録を作る
- 議事録の項目：要約、背景・目的、確認した要件（項目と内容）、懸念・課題、決定事項、次回までのアクション（担当・内容・期限）
- LLM への指示は sales_assist/prompts.py にテンプレートとしてまとめ、出力は JSON 形式にさせる
- LLM の呼び出し部分は差し替えられるようにし、今回は API キーなしで動く「モック」を実装する
  （モックは、商談メモの「話者：発言」からキーワードで簡易的に項目を埋めるだけでよい）
- 生成した議事録は保存し、次に開いたときも表示する
- テストも追加してください
```

**動作確認**：`testdata/04_短い商談メモ.txt` と `testdata/03_商談文字起こし_初回訪問.txt` の商談で議事録が表示されるか

### ステップ2-B：実際の LLM に近づける

実際の LLM は、JSON の前に「以下が結果です」と書いたり、```json で囲んだりすることがあります。
モックにその癖を再現させて、アプリが耐えられるかを確かめます。

```
ステージ2-B：実際の LLM に近づけるため、モックの応答を次の形に変えてください。
（前置きの一文）＋ ```json で囲んだ JSON ＋（締めの一文）
例は testdata/03_LLM応答サンプル_コードブロック付き.txt です。アプリ側のコードはまだ変更しないでください。
```

**動作確認**：議事録を生成する

### 想定される不具合

**不具合2-A：`json.decoder.JSONDecodeError: Expecting value: line 1 column 1` で画面が赤くなる**

- 原因：LLM の出力を `json.loads()` にそのまま渡している
- 修正プロンプト

```
【症状】ステージ2-B の変更後、「議事録を生成」を押すと JSONDecodeError が表示されます。
【再現手順】1. 商談を選ぶ 2. 「議事録を生成」を押す
【期待する動作】LLM の出力が ```json で囲まれていたり、前後に説明文があったりしても、JSON 部分を取り出して表示できる。
どうしても読めない場合は1回だけ再試行し、それでもだめなら「AI の出力を読み取れませんでした。もう一度お試しください。」と日本語で表示する（エラーの詳細や商談メモは画面に出さない）。
testdata/03_LLM応答サンプル_コードブロック付き.txt を使ったテストを追加してください。
```

**不具合2-B：項目が足りない JSON で `KeyError: 'decisions'`**

- 原因：LLM が一部の項目を省略した場合を想定していない
- 修正の方向：足りない項目を空のリストで補う処理を追加させる

## ステージ3 送信前マスキング（15分）

**ゴール**：AI に送る前に、個人情報と登録した固有名詞を置き換え、送る内容を確認できる

### プロンプト

```
ステージ3：AI に送る前のマスキング機能を作ってください。

- 電話番号とメールアドレスは自動で見つけて [電話番号] [メールアドレス] に置き換える
- 「マスキング設定」タブで、社名・人名などの語句と種類（会社名／人名／その他）を登録・削除できるようにする
- 登録した語句は [COMPANY_1] [PERSON_1] のような記号に置き換える。置き換えの対応表は AI に送らない
- 「議事録」タブで、AI に送る内容（マスキング済み）をプレビュー表示し、
  「確認しました」のチェックを入れないと生成ボタンを押せないようにする
- マスキング処理のテストを追加する
```

### 動作確認

1. 「マスキング設定」で「みらい商事株式会社」「みらい商事」（会社名）、「佐藤美和」「佐藤」「田中淳」「田中」（人名）を登録
2. `testdata/01_マスキング確認データ.txt` を商談として登録し、「議事録」タブでプレビューを見る
3. **6つの電話番号（全角・長音記号・ハイフンなし・かっこ付き・FAX を含む）と2つのメールアドレス** がすべて置き換わっているか
4. 「2026-10-20」（日付）が電話番号と間違えて置き換えられていないか
5. 「組織再編」は置き換わらない — **登録していない未公開情報は、マスキングでは守れない** ことを確認する

### 想定される不具合

**不具合3-A：全角の電話番号「０８０－４１２７－３３９５」や「080ー4127ー3395」が置き換わらない**

- 原因：正規表現が半角の数字とハイフンしか想定していない
- 修正プロンプト

```
【症状】全角数字の電話番号「０８０－４１２７－３３９５」と、長音記号「ー」を使った「080ー4127ー3395」がマスキングされません。
【再現手順】testdata/01_マスキング確認データ.txt を登録してプレビューを見る
【期待する動作】全角・半角、ハイフンの種類に関係なく [電話番号] に置き換わる。全角のメールアドレスも同様。
日付（2026-10-20 など）は置き換えないこと。testdata/01 のすべての行をテストにしてください。
```

**不具合3-B（修正の副作用）：直した後、議事録の「：」や「（）」が半角になった／話者が読み取れなくなった**

- 原因：全角を半角にするために、**文章全体** を正規化（NFKC）している
- 学べること：**不具合を直すと、別の場所に影響が出ることがある**。だからテストで守る
- 修正プロンプト

```
【症状】マスキングの修正後、議事録の全角の「：」「（）」が半角になり、話者の区切りが読み取れない行があります。
【期待する動作】電話番号・メールアドレスの検出に必要な文字（全角の英数字と＠．－など）だけを半角にし、文章のその他の部分は変えない。
既存のテストがすべて通ることを確認してください。
```

**不具合3-C：「みらい商事」を先に置き換えたため「[COMPANY_1]株式会社」が残る／「佐藤」だけ置き換わり「[PERSON_1]美和」になる**

- 修正の方向：長い語句から順に置き換えるよう依頼する。氏名は「佐藤美和」と「佐藤」の両方を登録する
- 自動文字起こしの話者は「話者A／B／C」なので、話者ラベル自体は個人情報ではないが、自己紹介の発言に氏名が出てくる点に注意

### 完了チェック

- [ ] testdata/01 の電話番号・メールアドレスがすべて置き換わる
- [ ] プレビューで確認しないと生成できない
- [ ] 「マスキングは万能ではない（組織再編）」ことを確認した

## ステージ4 名前の復元とメール下書き（15分）

**ゴール**：議事録に元の名前が表示され、議事録からメールの下書きを作れる

### 動作確認（ステージ3の直後にまず確認）

ステージ3の状態で議事録を生成すると、**議事録に `[PERSON_3]` のような記号が残っている** はずです。
これは不具合でしょうか？ — AI には記号で送る必要がありますが、**人が読む画面では元の名前に戻す** 必要があります。

### プロンプト

```
ステージ4：
1. AI の出力（議事録）に含まれる [COMPANY_1] [PERSON_1] などの記号を、表示・保存の前に元の語句へ戻してください。
   [電話番号] [メールアドレス] は元に戻さないでください。
2. 「メール下書き」タブを作ってください。
   - 商談を選び、宛先（顧客／社内）とトーン（丁寧／標準／簡潔）、差出人を選んで下書きを作る

## ステージ5 行動管理（20分・持ち帰り課題）

**ゴール**：議事録のアクションが期限順に一覧になり、期限切れが分かる

### プロンプト

```

- 期限を過ぎていて未完了のものは目立つように表示する（判定に使う「今日の日付」はサイドバーで変更できるようにする）
- テストを追加してください
```

### 動作確認

1. `testdata/02_期限表現確認データ.txt` を **商談日 2026-10-06** で登録し、議事録を生成
2. 行動管理の期限が次のようになっているか

| 今週金曜までに | 2026/10/09（金） |
| 来週月曜までに | 2026/10/12（月） |
| 来週火曜までに | 2026/10/13（火） |
| 明日 | 2026/10/07（水） |
| 10月15日までに | 2026/10/15（木） |
| 1月15日までに | **2027**/01/15（金） |
| 次回 | 要確認 |

3. サイドバーの「今日の日付」を 2026-10-14 にすると、10/9・10/12・10/13 期限のものが期限切れになるか

### 想定される不具合

**不具合5-A：期限が「今週金曜」のまま保存され、並び順がおかしい／期限切れの判定でエラー**

```
ValueError: Invalid isoformat string: '今週金曜'
```

- 原因：AI が返した期限の表現を、そのまま日付として扱っている
- 修正プロンプト

```
【症状】行動管理を開くと ValueError: Invalid isoformat string: '今週金曜' が表示されます。
【期待する動作】「今週金曜」「来週月曜」「来週火曜」「明日」「10月15日」「1月15日」のような期限の表現を、
**商談日を基準に** 具体的な日付に変換して保存する。変換できないもの（「次回」など）は「要確認」と表示し、画面から期限を設定できるようにする。
元の表現も保存しておく。testdata/02 の表をテストにしてください。
```

**不具合5-B：期限が1週間ずれる（今日を基準に計算している）**

- 起きやすい状況：Codex が「来週」を **今日の日付** から計算した。商談日と登録日が違うとずれる
- 学べること：**「何を基準にするか」を指示で明確にする** ことの大切さ。テストの期待値（上の表）で気付ける

**不具合5-C：「1月15日」が 2026年1月（過去）になる**

- 修正の方向：「商談日より大きく過去になる場合は翌年とみなす」ルールを伝える

**不具合5-D：議事録を再生成するとアクションが重複する／期限が未定のものが先頭に来る**

- 修正の方向：「再生成したときは、その商談のアクションを置き換える」「期限が未定のものは最後に並べる」と伝える

## 付録C 講師用：ストーリーが崩れたときの対応

| 状況 | 対応 |
|---|---|
| Codex が最初から不具合のないコードを作った | 「動作確認」の手順で問題がないことを確かめさせ、**確認用データの意図**（なぜ全角の電話番号を試すのか）を説明する。テストが追加されているかを確認させる |
