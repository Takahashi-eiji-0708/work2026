# 第1章 生成AIの進化と現状

## 1.1 AIの歩み

| 時期 | 出来事 | ポイント |
|---|---|---|
| 1950〜60年代 | 第1次AIブーム（探索・推論） | パズルや迷路は解けるが、現実の問題には使えなかった |
| 1980年代 | 第2次AIブーム（エキスパートシステム） | 専門家の知識をルールとして書き込む。ルールの作成・保守が限界に |
| 2000年代〜 | 第3次AIブーム（機械学習・深層学習） | データから規則性を自動で学ぶ。2012年ごろから画像認識の精度が急速に向上 |
| 2017年 | Transformer の発表 | 文章中の単語同士の関係をまとめて捉える仕組み。今の生成AIの土台 |
| 2022年11月 | ChatGPT の公開 | 誰でも会話で使える生成AIが登場し、利用者が爆発的に増える |
| 2023年 | マルチモーダル化・業務ツールへの組み込み | 画像も理解できるモデルが登場。Microsoft 365 に Copilot が組み込まれ始める |
| 2024年 | 推論モデルの登場 | 答える前に「考える」時間を取り、複雑な問題の正答率が向上 |
| 2025年〜 | エージェントの普及 | 調べる・資料を作る・コードを書くなど、複数の手順をAIが自律的に進める |

**現在（2026年）の状況**
生成AIは「質問に答える道具」から「仕事の一部を任せられる同僚」に近づいています。
Word・Excel・PowerPoint の中から直接AIを呼び出せるようになり、
資料作成の流れを変えずにAIを使えるようになりました。
一方で、AIに渡した情報の扱いや、AIが作ったものの正しさに対する **人間の責任** はむしろ重くなっています。

## 1.2 大規模言語モデル（LLM）の仕組み

生成AIの中心にあるのは **大規模言語モデル（LLM）** です。仕組みを一言でいうと、
**「それまでの文章に続く、もっともらしい次の言葉を予測し続ける」** プログラムです。

```
入力：「お打ち合わせのお時間をいただき、誠に」
予測：「ありがとう」(82%)  「感謝」(9%)  「恐縮」(4%) ...
      → 確率に従って1語選び、それを入力に加えて次を予測…を繰り返す
```

この仕組みから、次の性質が生まれます。

| 性質 | 業務への影響 |
|---|---|
| 同じ質問でも毎回答えが少し変わる | 気に入らなければ再生成する。一方、同じ結果の再現は保証されない |
| もっともらしい嘘をつくことがある（**ハルシネーション**） | 数字・固有名詞・日付・出典は必ず確認する |
| 学習した時点以降の情報を知らない | 最新情報は Web 検索機能を使い、出典を確認する |
| 指示（プロンプト）の質で結果が大きく変わる | 目的・前提・出力形式をはっきり伝える（第2章） |
| 計算や厳密な集計は苦手 | 計算は Excel の数式に任せ、AIには数式を作らせる（第6章） |

## 1.3 生成AIの得意・不得意

| 得意なこと | 苦手なこと・注意が必要なこと |
|---|---|
| 文章の下書き・言い換え・要約 | 正確な事実の保証（特に数字・固有名詞） |
| アイデア出し・観点の洗い出し | 最新の出来事（検索機能なしの場合） |
| 文章の構造化（箇条書き・表への変換） | 厳密な計算・大量データの正確な集計 |
| トーンの調整（丁寧・簡潔・説得的） | 顧客との関係性や社内事情をふまえた判断 |
| 数式・コードの作成と説明 | 責任を伴う最終判断 |

> **営業での原則**：AIは「下書き担当」「壁打ち相手」。**最終確認と判断は必ず人が行う。**

# 第2章 Copilot の基本操作とプロンプト設計

## 2.1 Copilot アプリの基本操作

| 操作 | 説明 |
|---|---|
| 新しいチャット | 話題が変わったら新しいチャットを始める（前の会話の影響を受けないように） |
| 入力欄 | 質問や指示を入力する。Shift＋Enter で改行 |
| 応答モードの切り替え | 素早く答えるモードと、じっくり考えて答えるモードがある（名称は画面で確認） |
| Web 検索と出典 | 最新情報を検索して答える。回答内の **出典リンク** を必ず開いて確認する |
| ファイル・画像の添付 | ファイルを読み込ませて質問できる。**添付してよい情報かを先に判断する** |
| コピー・再生成・評価 | 回答のコピー、別の回答の生成、良し悪しのフィードバック |
| 履歴 | 過去のチャットを開き直す・削除する |

## 2.2 Office アプリで Copilot を使う前提

- **ファイルを OneDrive に保存し、自動保存をオンにする**（ローカル保存のままだと、Excel などで Copilot を使えない場合がある）
- Premium の Microsoft アカウントで Office にサインインしている
- リボンの **Copilot ボタン**、または文書内に表示される Copilot アイコンから呼び出す

## 2.3 伝わるプロンプトの4要素

| 要素 | 内容 | 例 |
|---|---|---|
| **役割** | AIにどの立場で考えてほしいか | あなたは法人向け研修の提案に詳しい営業コンサルタントです |
| **目的** | 何のために、何を作ってほしいか | 初回訪問で聞くべき質問を洗い出したい |
| **前提・制約** | 背景、相手、条件、してほしくないこと | 顧客は商社の人材開発担当者。所要時間は60分。予算と決裁の進め方の質問は最後に |
| **出力形式** | 形式・分量・構成 | 目的別に5つの分類で、各3問、表形式で |

> Microsoft は「**目的（Goal）・背景（Context）・情報源（Source）・期待（Expectations）**」の4つを伝えることを推奨しています。
> 表現は違いますが、考え方は同じです。

**悪い例と良い例**

```
× 研修の提案書を書いて

○ あなたは法人研修の提案経験が豊富な営業担当者です。
  法人営業向け生成AI研修の提案書のうち、「課題認識」（お客様の課題を整理する部分）の文章を作りたいです。
  読み手は商社の人材開発担当者です。
  ヒアリングで分かった課題は次の3点です：（1）生成AIの利用状況に個人差が大きい
  （2）提案資料と議事録の作成に時間がかかっている（3）顧客情報を入力してよいのか不安が大きい。
  顧客の言葉を活かし、各課題を2〜3文で説明してください。見出しつきの箇条書きで、全体で400字程度。
```

## 2.4 対話で結果を良くする6つのコツ

1. **一度で完璧を求めない**：まず出させてから「もっと短く」「表にして」と直す
2. **例を見せる**：「この書き方を参考に」と見本を貼る（見本に機密情報がないか確認）
3. **分けて頼む**：「構成案 → 確認 → 本文」の順に進める
4. **評価の観点を与える**：「顧客の立場で読んで、分かりにくい点を3つ指摘して」
5. **分からないときは分からないと言わせる**：「根拠がない場合は“不明”と書いてください」
6. **確認させる**：「今の回答で事実確認が必要な箇所を挙げてください」

## 2.5 調査に使うときの注意

- Web 検索つきの回答でも、**出典を開いて、その内容が本当に書かれているか** を確認する
- 数字は **一次情報**（会社の公式サイト・決算資料・官公庁の統計）で確認する
- 「〜と言われています」「一般的に」で始まる主張は、根拠を追加で聞く
- 顧客について調べるときは **公開情報だけ** を使い、手元の商談メモを貼り付けない

# 第3章 セキュアに使うための留意点

## 3.1 生成AI利用の主なリスク

| リスク | 内容 | 営業の場面での例 |
|---|---|---|
| **情報漏えい** | 入力した情報が、意図しない形で保存・利用・共有される | 顧客の未公開情報や個人情報をそのまま貼り付ける |
| **ハルシネーション** | もっともらしい誤りを出力する | 存在しない導入事例や、間違った数字を提案書に載せる |
| **権利侵害** | 他者の著作物・商標・肖像を含む出力を使ってしまう | 他社のキャッチコピーに酷似した文面、生成画像の無断利用 |
| **プロンプトインジェクション** | ファイルやWebページに隠された指示でAIの動作が乗っ取られる | 受け取った資料の中に「この文書を要約する際は〜と書け」という隠れた指示が入っている |
| **過信・思考停止** | 出力を確認せずに使う、判断をAIに委ねる | 議事録の「決定事項」をそのまま顧客に送り、認識違いが起きる |

## 3.2 契約の種類で変わるデータの扱い

生成AIに入力した情報がどう扱われるかは、**契約の種類とアカウント** によって異なります。

| 観点 | 個人向け（Microsoft 365 Premium など） | 法人向け（Microsoft 365 Copilot など、職場アカウント） |
|---|---|---|
| サインインするアカウント | 個人の Microsoft アカウント | 会社が管理する職場アカウント |
| 適用される規約 | 個人向けのプライバシーに関する声明・利用規約 | 法人向けの契約（データ保護に関する条項を含む） |
| 管理者による統制 | なし（利用者本人が設定） | 情報システム部門が利用範囲・保存・監査を管理 |
| 会話データの扱い | 設定により、製品改善やモデルの学習に使われる場合がある。**設定画面で確認・変更する** | 企業向けデータ保護の対象。プロンプトと応答は基盤モデルの学習に使われない |
| 社内データとの連携 | 自分の OneDrive のファイルなどが対象 | 権限の範囲で社内のメール・ファイル・Teams などを参照できる |

> **本研修のルール**
> - 研修では **架空のデータだけ** を使う
> - 実際の顧客情報・社内情報は **会社が認めた法人契約の環境** で、**会社のガイドラインに従って** 扱う
> - 個人契約の Copilot を業務ファイルに使ってよいかは、**会社のルールを確認する**（禁止されている会社も多い）
> - 規約や設定項目は変わることがあるため、利用開始時と定期的に確認する

## 3.3 入力してよい情報の3段階判定

| 判定 | 意味 | 例 |
|---|---|---|
| **A：入力可** | 公開情報・一般的な知識 | 顧客のホームページに載っている情報、業界の一般的な動向、自分で考えた文章 |
| **B：加工すれば可** | 特定できないように加工すれば使える | 社名・人名を伏せた商談の論点、具体的な金額を幅に置き換えた価格情報 |
| **C：入力不可** | 加工しても入力してはいけない | 個人情報（連絡先・人事評価など）、顧客の未公開情報、秘密保持契約の対象、自社の社外秘の方針、ID・パスワード |

**判定に迷ったら**：「この情報が、そのまま社外の掲示板に貼られても問題ないか？」と考える。問題があれば B か C。迷ったら C として扱い、上長に相談する。

## 3.4 マスキングの4つの技法

| 技法 | 方法 | 例 |
|---|---|---|
| **置換** | 固有名詞を記号に置き換える | みらい商事株式会社 → 商社A社／佐藤美和 → 顧客担当者X |
| **一般化** | 具体的な値を幅や分類にする | 競合は1名あたり約4万円 → 競合は中程度の価格帯 |
| **削除** | 目的に不要な情報を消す | 携帯電話番号・メールアドレス・雑談 |
| **抽象化** | 事実を課題の型に置き換える | 未公表の組織再編の計画 → （入力しない。必要なら「組織変更の可能性」程度に） |

**マスキングのコツ**

- 置き換えの対応表（A社＝みらい商事 など）は **手元のメモで管理** し、Copilot には渡さない
- 出力を使うときに、手作業で元の名前に戻す
- 全角・半角、ハイフンの有無など、**表記のゆれ** で消し漏れが起きやすい（第9章のアプリでも課題になります）

## 3.5 ハルシネーションへの対策

| 確認の対象 | 確認方法 |
|---|---|
| 数字 | 元データ・一次情報と照合する。計算は Excel で検算する |
| 固有名詞・社名・役職 | 名刺・CRM・公式サイトで確認する |
| 日付・曜日 | カレンダーで確認する。「来週金曜」のような相対的な表現は具体的な日付に直す |
| 出典 | リンクを開き、本当にその内容が書かれているかを確認する |
| 決定事項・約束 | 自分のメモ・記憶と照合する。曖昧なら相手に確認する |

## 3.6 プロンプトインジェクションへの注意

外部から受け取った文書・Webページ・メールには、**AIへの指示を装った文章** が紛れ込んでいることがあります。

- 他人から受け取ったファイルを Copilot に要約させた結果が、**不自然な指示や誘導** を含んでいたら使わない
- AIがメール送信やファイル操作を自動で行う機能（エージェント）を使うときは、**実行前に内容を確認** する
- 生成された文章にある **見覚えのないリンク** は開かない

## 3.7 出力を使うときの注意

- 社外に出す文書は、**自分の言葉として責任を持てるか** を確認してから使う
- 他社の商標・ロゴ・キャッチコピーに似ていないか確認する
- 生成した画像を提案資料に使う場合は、会社のルールと利用条件を確認する
- 共有リンクを発行するときは、**共有範囲**（組織内のみ／リンクを知っている全員 など）を確認する

## 3.8 セキュア活用の7つのルール（まとめ）

1. **入力前に判定**：A（入力可）／B（加工すれば可）／C（入力不可）を判断する
2. **B はマスキング**：置換・一般化・削除・抽象化してから入力する
3. **C は入力しない**：個人情報・未公開情報・社外秘・認証情報
4. **出力は検証**：数字・固有名詞・日付・出典を確認する
5. **最後は人が判断**：送信・提出・約束は人が決める
6. **契約とルールを確認**：会社のガイドラインと、使っている契約のデータ保護を確認する
7. **困ったら相談**：迷ったら使わず、上長・情報システム部門に相談する

# 第4章 Word × Copilot：商談準備と議事録

## 4.1 Word での Copilot の主な使い方

| 機能 | 使う場面 | 操作の例 |
|---|---|---|
| **下書き** | 白紙から文書を作る | 新規文書で Copilot を呼び出し、作りたい文書を指示する |
| **ファイルを参照した下書き** | 既存の資料をもとに作る | 指示の中で参照ファイルを指定する（「/」を入力してファイルを選ぶ など） |
| **書き換え** | 選択した文章を直す | 文章を選択 → Copilot アイコン → 書き換え・トーン変更 |
| **表に変換** | 文章を表に整理する | 選択した箇条書きを表形式に変換する |
| **要約** | 長い文書の要点を知る | Copilot ウィンドウで「この文書を要約して」 |
| **質問** | 文書の内容を確認する | 「この文書で期限が書かれている作業をすべて挙げて」 |

## 4.2 議事録を作るときのポイント

文字起こしをそのまま要約させると、次のような問題が起きがちです。

| よくある問題 | 対策（プロンプトに入れる指示） |
|---|---|
| 雑談まで議事録に入る | 「業務に関係しない雑談は除外してください」 |
| 「来週金曜」が残る | 「相対的な日付は、会議日（2026年10月6日）を基準に具体的な日付（曜日つき）に直してください」 |
| 誰の発言・約束かが曖昧 | 「アクションは担当者・内容・期限の表にしてください。担当が不明な場合は“要確認”と書いてください」 |
| 推測で決定事項が作られる | 「会議で明確に合意されたことだけを決定事項にし、それ以外は“検討事項”にしてください」 |
| 社名・氏名が残る | **Copilot に渡す前に** 社名・氏名を記号に置き換える（「佐藤美和」「佐藤」のように長い語から） |
| 話者が「話者A／B／C」のまま | 冒頭の自己紹介から話者を特定し、「話者A＝ELI 高橋」のように対応を示す |
| 決まっていないことが決定事項になる | 「未確定のことは“未確定事項”として分け、担当・期限が決まっていなければそう書いてください」 |

**議事録の型**

```
1. 会議の概要（日時・場所・出席者）
2. 背景・目的
3. 確認した要件
4. 懸念・課題
5. 決定事項
6. 次回までのアクション（担当・内容・期限）
```

# 第5章 商談後フォロー：メール・社内報告・行動管理

## 5.1 相手と目的に合わせて書き分ける

| 文書 | 読み手 | 目的 | 書き方のポイント |
|---|---|---|---|
| 議事録送付メール | 顧客（CC を含む） | 感謝と認識合わせ、Next Action の共有 | 丁寧に、要点を箇条書きで。**未確定事項を確定したように書かない** |
| 社内報告 | 上長 | 状況共有と相談 | 結論 → ポイント → 相談 → 次の一手。短く |
| 行動リスト | 自分・チーム | 抜け漏れ防止 | 誰が・何を・いつまでに・状態 |

## 5.2 メールを Copilot で作るときの注意

- 議事録をもとに作る場合、**自社の社内事情・社内の相談事項** が顧客向けメールに混ざっていないか、**未確定事項を確定したように書いていないか** 確認する
- 「丁寧すぎる」「長すぎる」ときは「ビジネスメールとして標準的な丁寧さで、300字以内に」と調整する
- 宛名・敬称・社名・日付は **自分で必ず確認する**
- 送信は必ず人が行う

## 5.3 社内報告の型

```
【結論】受注確度・次のマイルストーン
【ポイント】ニーズ／決め手／リスク（各1行）
【ご相談】上長に判断・支援してほしいこと
【次の一手】日付つきの予定
```

## 5.4 行動管理：議事録から「やること」を抜き出す

商談後の作業は **議事録 → メール → 行動リスト** の順に、同じ情報を形を変えて何度も使います。
この繰り返しの作業をまとめて支援するのが、第9章で紹介する **ELI Sales Assist** です。

# 第6章 Excel × Copilot：分析と見積

## 6.1 Excel で Copilot を使う前の準備

- データを **テーブル**（挿入 → テーブル）にしておく。見出しは1行、結合セルは使わない
- ファイルは OneDrive に保存し、自動保存をオンにする
- 列名は意味が分かる名前にする（「列1」ではなく「満足度」など）

## 6.2 Excel での Copilot の主な使い方

| やりたいこと | 依頼の例 |
|---|---|
| データの概要をつかむ | 「このデータから分かる傾向を3つ教えて」 |
| 集計・比較 | 「実施形式ごとの満足度の平均を比較して」 |
| 数式列の追加 | 「受講者1人あたり受講料の列を追加して」 |
| 強調表示 | 「満足度が4.5以上の行を強調して」 |
| グラフ・ピボット | 「カテゴリ別・年度別の受講者数をグラフにして」 |
| 高度な分析 | 「事後フォローの有無で1か月後活用率に差があるか分析して」 |
| 数式の説明 | 「この数式が何をしているか説明して」 |
| 文章の分類 | 「自由記述を内容でグループ分けして、件数を数えて」 |

## 6.3 分析結果を使うときの注意

- Copilot の集計結果は、**ピボットテーブルや関数で自分でも検算** する
- データの **表記ゆれ・空欄** があると結果がずれる。先に「データの品質で気になる点はある？」と聞く
- 「差がある」と言われたら、件数（n数）が十分か、他の要因が混ざっていないかを考える
- 見積など **お金に関わる計算** は、Copilot に数式を作らせ、人が一行ずつ確認する

# 第7章 Word × Copilot：提案書の作成

## 7.1 提案書づくりの流れ

```
① 構成を決める（テンプレートの章立て）
② 章ごとに材料を集める（議事録・分析結果・見積・研修プログラム案）
③ Copilot で章ごとに下書きする（参照ファイルを指定）
④ 顧客の立場で読み直す（Copilot にレビューさせる → 人が判断）
⑤ 事実確認・体裁を整える
```

## 7.2 良い提案書にするための指示

- 「**顧客の言葉** を使って課題を書いて」— 議事録の表現を活かすと、顧客に響く
- 「**根拠となる数字** を入れて」— 演習9の分析結果を使う（数字は自分で確認したもの）
- 「**他社との違い** が伝わるように」— 特長は3つ程度に絞る
- 最後に「人材開発担当の上長（判断する人）の立場で読んで、**判断に困る点** を指摘して」と頼む
- **A案・B案の2案** を出すときは、違い（日数・内容・フォロー・金額）を比較表にし、「どんな状況ならどちらを選ぶか」を書く
- 効果は **過大に書かない**。削減時間を人件費削減や売上増にそのまま換算しない

## 7.3 提案書のチェックリスト

- [ ] 顧客名・担当者名・日付は正しいか
- [ ] 数字は自分で確認した値か（Copilot が作った数字をそのまま使っていないか）
- [ ] 未公開情報・他社情報・社内事情を書いていないか
- [ ] 存在しない事例や実績を書いていないか
- [ ] 顧客の課題とプログラム内容が対応しているか

# 第9章 自社アプリ ELI Sales Assist の紹介

## 9.1 なぜアプリにするのか

第4〜5章では、商談後に次の作業を Copilot で行いました。

```
文字起こし → [マスキング] → 議事録 → 議事録送付メール → 社内報告 → 行動リスト・確認事項
```

毎回同じプロンプトを書き、同じチェックをしていることに気付いたでしょうか。
**繰り返す作業・毎回同じ確認が必要な作業** は、プロンプトとチェックを組み込んだアプリにすることで、
品質をそろえ、セキュリティ対策の漏れを防げます。

## 9.2 ELI Sales Assist の機能

| 機能 | 内容 |
|---|---|
| 商談の登録 | 顧客名・日付・出席者・商談メモ（文字起こし）を登録 |
| **マスキング** | 電話番号・メールアドレス・登録した固有名詞を自動で置き換え、AIに送る前にプレビュー表示 |
| **議事録生成** | 決まった型（概要・要件・懸念・決定事項・アクション）で議事録を生成 |
| **メール下書き** | 議事録をもとに、宛先の種類（顧客・社内）とトーンを選んで下書きを作成 |
| **行動管理** | 議事録から抽出したアクションを一覧化。期限切れの強調、状態の更新、CSV出力（Excelで開ける） |

## 9.3 仕組み

```
[画面(Streamlit)]
   │ 商談メモ
   ▼
[マスキング処理] ── 置換表はアプリ内だけで保持（AIには送らない）
   │ マスキング済みテキスト
   ▼
[プロンプトテンプレート] ── 役割・目的・出力形式(JSON)を固定
   │
   ▼
[LLM API]（または教材用のモック） ── 構造化された結果(JSON)を返す
   │
   ▼
[結果の検証・復元] ── JSONの形式チェック、相対日付→具体的な日付、置換した名前を元に戻す
   │
   ▼
[データベース(SQLite)] ── 商談・議事録・アクションを保存
```

## 9.4 アプリに組み込まれたセキュリティ対策

| 対策 | 内容 | 第3章との対応 |
|---|---|---|
| 送信前マスキング | 個人情報・固有名詞を置き換えてから AI に送る | 3.4 マスキング |
| 送信内容のプレビュー | 何を送るかを人が確認してから実行 | 3.8 ルール1・5 |
| API キーの管理 | キーはコードに書かず環境変数で管理。リポジトリに含めない | 3.1 情報漏えい |
| ログの最小化 | 商談の本文をログに出さない | 3.1 情報漏えい |
| 出力の検証 | AIの出力形式をチェックし、日付を具体化。最終確認は人 | 3.5 ハルシネーション |

## 9.5 アプリの限界

- マスキングは **登録した名前・決まったパターン** にしか効かない。**最後は人が確認する**
- AIの出力は毎回変わる。議事録・メールは **下書き** として扱う
- 本アプリは研修用のサンプルです。業務で使う場合は、会社の承認・法人契約の API・セキュリティ審査が必要です

# 第10章 営業業務への応用

## 10.1 応用を考える4ステップ

```
STEP1 業務の棚卸し   … 1週間の業務を書き出す
STEP2 候補の選定     … 頻度が高い × 定型的 × 時間がかかる業務を選ぶ
STEP3 効果とリスク   … 削減できる時間、扱う情報の判定（A/B/C）
STEP4 実現方法の選択 … 下の表から選ぶ
STEP5 試す・直す     … 小さく試し、結果を見て改善する
```

## 10.2 実現方法の選び方

| レベル | 方法 | 向いている業務 |
|---|---|---|
| 1 | Copilot にその都度プロンプトを書く | 頻度が低い、毎回内容が違う |
| 2 | **プロンプトテンプレート** を作って使い回す | 頻度が高い、型が決まっている |
| 3 | Copilot のノートブック・カスタム指示など、**文脈を保存する機能** を使う | 同じ資料を何度も参照する |
| 4 | **アプリにする**（ELI Sales Assist のように） | 複数の手順がつながっている、チームで品質をそろえたい、セキュリティ対策を仕組みで担保したい |

## 10.3 AIと一緒にアプリを作る（Codex）

プログラミングの経験が少なくても、コーディング用のAIエージェント（OpenAI Codex など）を使えば、
**日本語で指示しながらアプリを作る** ことができます。進め方のコツは次のとおりです。

1. **最初にルールを書く**：作るものの目的・技術・禁止事項を `AGENTS.md` にまとめる
2. **小さく作って動かす**：一度に全部を頼まず、1機能ずつ作って動作確認する
3. **不具合は症状と再現手順で伝える**：「動かない」ではなく「〇〇を入力して△△を押すと、××というエラーが出る」
4. **テストを書かせる**：直した不具合が再発しないように、テストも一緒に作らせる
5. **生成されたコードも確認する**：API キーの直書き・不要な通信・ログへの機密出力がないか

詳しくは演習14と `codex/Codex開発プロンプト集.md` を参照してください。

## 10.4 社内で広げるときの注意

- 会社のガイドラインと契約（法人向けのデータ保護）を確認し、必要な承認を得る
- 良いプロンプトはチームで共有し、**「入力してはいけない情報」の注意書き** とセットで使う
- 効果（削減時間・品質）を記録し、上長に報告できるようにする
